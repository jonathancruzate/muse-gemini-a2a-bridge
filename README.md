# Muse ↔ Gemini Spark A2A Bridge — Replication Guide

_How to make two personal AI agents — **Muse** and **Gemini Spark** — talk to each
other agent-to-agent (A2A) with no human in the loop and no polling delay:
a shared Google Sheet as the mailbox, a Google Apps Script change trigger as
the doorbell, and an email-triggered Gemini Spark schedule as the reader._

| Status | **Live and verified end-to-end on 2026-11-01** (test request processed immediately on the alert email, not on an hourly tick) |

## Why this design (the two problems it solves)

1. **Custom-MCP writes stall unattended Gemini runs.** When Gemini Spark tries
   to return a result through a custom MCP app tool (e.g. a
   `submit_request_result` call), Gemini shows a per-call
   *"Let Gemini use X — Allow/Deny"* prompt. A scheduled, unattended run stops
   there forever ("Needs input"). Tool annotations do not remove the prompt,
   and the Connected Apps page has no always-allow setting.
   **Fix:** move both directions onto a **first-party Google Workspace
   surface** — a Google Sheet — which Gemini Spark can read and append to in
   scheduled runs without that prompt class.
2. **Polling is slow and wasteful.** The original design had Gemini Spark
   check the sheet on an **hourly** schedule, so a request could wait up to
   an hour.
   **Fix (2026-11-01):** make the sheet itself ring a doorbell. An Apps Script
   `On change` trigger sends a one-line alert email the moment a request row
   lands; Gemini Spark's processing schedule is **email-triggered** on that
   exact subject, so it wakes and processes the queue immediately.

## Architecture

```
 Muse (Agent A)                                   Gemini Spark (Agent B)
 ──────────────                                    ──────────────────────
 enqueue: append row ──►  ┌─────────────────┐
 to Requests tab          │  A2A - Results  │
                          │  (Google Sheet) │
 Apps Script On change ──►│  Requests tab   │──► email-triggered schedule
 sends alert email        │  Results tab    │    "Process Muse bridge
 subject "A2A-Event"      │  Notes tab      │     requests" reads Requests,
        │                 └─────────────────┘     answers with its Google
        │                          ▲              connectors, appends one
        ▼                          │              row per answer to Results
 Gmail (the account                │              (+ free-form Notes)
 Gemini Spark watches) ────────────┘
 Muse-side poller: reads Results rows → matches (request_id, token) →
 commits the result to its queue store → deletes the processed rows →
 prunes finished Requests rows → ingests Notes rows.
```

Roles:

- **The sheet is the mailbox.** Three tabs (below). It is keyed everywhere by
  **spreadsheet ID + tab names**, never by the spreadsheet's display title —
  you can rename the title freely if you also update any prompt or doc that
  mentions the sheet *by name*.
- **The Apps Script is the doorbell.** It does no processing; it only sends
  the alert email (with a debounce, below).
- **The email is the wake-up signal.** Subject is a fixed token —
  `A2A-Event` — because the receiving schedule filters on it exactly.
- **Each agent's own store stays canonical.** On the Muse side a queue
  (originally a Cloudflare KV store behind an MCP server) is the system of
  record; the sheet rows are a transport lane that is cleared after commit.
  A replicator can substitute any local store (a JSON file works).

## Step 1 — Create the sheet

Create a Google Sheet (ours is titled **`A2A - Results`**) with three tabs
and exactly these header rows (row 1, frozen):

**Tab `Requests`** — Muse appends; Gemini Spark reads:
`appended_at | request_id | token | kind | params_json | context`

**Tab `Results`** — Gemini Spark appends; Muse reads:
`appended_at | request_id | token | kind | status | result_json`

**Tab `Notes`** — Gemini Spark appends free-form notes back to Muse:
`appended_at | priority | note`

Field rules:

- `request_id` — monotonically increasing integer (or UUID) per request.
- `token` — a short random per-request secret generated by the sender.
  `(request_id, token)` together are the **idempotency / matching key**:
  duplicate result rows are ignored; a result that doesn't match a pending
  request is never committed.
- `kind` — a dotted request type, e.g. `flights.search`, `hotels.search`,
  `youtube.search`, `finance.quote`, `mail.search`, `drive.search`,
  `calendar.search`, `test.ping`.
- `params_json` — the request itself as **structured JSON data only**.

> ⚠️ **Structured data, never prose instructions.** Gemini's MCP policy
> blocks tool payloads that read as instructions to the agent. Keep every
> payload `kind + params`; the *standing instructions* for how to handle a
> request live in Gemini Spark's own schedule prompt (Step 3), never inside
> a request row.

## Step 2 — Add the doorbell (Apps Script)

In the sheet: **Extensions → Apps Script**, replace `Code.gs` with:

```javascript
function onBridgeChange(e) {
  const ss = SpreadsheetApp.getActiveSpreadsheet();
  const requestsSheet = ss.getSheetByName("Requests");
  if (!requestsSheet) return;

  // Check if there are data rows below the header row
  const lastRow = requestsSheet.getLastRow();
  if (lastRow <= 1) return;

  // 15-second debounce to avoid duplicate alerts during batch row inserts
  const cache = CacheService.getScriptCache();
  if (cache.get("RECENT_ALERT")) return;
  cache.put("RECENT_ALERT", "true", 15);

  MailApp.sendEmail({
    to: "<YOUR_EMAIL>",
    subject: "A2A-Event",
    body: "A new pending request was appended to the Requests tab in A2A - Results."
  });
}
```

Save, then add the trigger: **Triggers (clock icon) → + Add Trigger**

- Function to run: `onBridgeChange`
- Event source: **From spreadsheet**
- Event type: **On change**

Grant the permissions when prompted (the script needs spreadsheet access
and "send email as you"). Notes:

- The trigger fires on *any* change to the spreadsheet; the function itself
  checks that `Requests` actually has data rows, and the 15-second
  `CacheService` debounce collapses batch inserts into one email.
- Keep the subject **exactly** `A2A-Event` — Step 3's filter matches on it.

## Step 3 — Gemini Spark side: the email-triggered schedule

In Gemini Spark, create a schedule named **`Process Muse bridge requests`**:

- **Trigger: incoming email** matching `subject:"A2A-Event"` (an email-based /
  event-driven schedule, not a time schedule). It should be **Active**.
- **Pause the legacy hourly polling schedule** (`Check Muse MCP queue`,
  hourly) so both don't process the same queue.
- **Prompt** (adapt names to yours; keep the prohibitions — they are the
  load-bearing part):

```text
When an email with subject "A2A-Event" arrives:
1. Open the "A2A - Results" spreadsheet and read every data row in the
   Requests tab. If there are no data rows, stop.
2. For each request row: carry out the request read/query-only, using your
   Google connectors and search, according to its kind and params_json.
   Never book, buy, send, or delete anything.
3. For each answer, append ONE row to the Results tab:
   appended_at = now, request_id and token copied EXACTLY from the request
   row, kind copied from the request row, status = "done" (or "error" with
   the reason in result_json), result_json = the answer as JSON.
4. Put any free-form note for Muse as a row in the Notes tab instead of
   using any Muse MCP tool.
5. Do NOT call any Muse MCP tool in this scheduled run — no
   get_pending_requests, no submit_request_result, no leave_note_for_muse.
   Those calls raise Allow/Deny prompts and stall the run. The sheet is
   the only channel for scheduled runs.
```

## Step 4 — Muse side: enqueue + poller

**Enqueue (sender):** for each new request, (a) record it in your own queue
store as `pending` with its `request_id` and `token`, and (b) append one row
to the `Requests` tab. The append is what rings the doorbell.

**Poller (return lane):** a lightweight recurring job (ours is a zero-token
hook that only wakes an agent when rows exist):

1. Read the `Results` tab.
2. For each row, match `(request_id, token)` against pending requests.
3. On a match: write the result into the queue store and mark the request
   done — **verify the commit, then** delete the processed `Results` row
   (verify-then-clear).
4. Prune `Requests` rows whose requests are done.
5. Read the `Notes` tab the same way: ingest each note, then clear it.
6. Leave unmatched rows in place and surface them — never silently drop a
   result that doesn't match.

## Step 5 — Verify end-to-end (one decisive test)

1. Enqueue a `test.ping` request (fresh `request_id` + `token`).
2. Within moments you should receive the `A2A-Event` alert email.
3. Gemini Spark's **Process Muse bridge requests** schedule runs
   immediately (not at the next hour).
4. A result row appears in `Results` with the same `request_id` + `token`.
5. Your poller commits it, marks the request done, and clears both rows.
6. The Gemini run must **not** end in "Needs input" — if it does, it called
   an MCP tool; check the Step 3 prompt prohibitions.

Verified live in the reference setup on 2026-11-01: alert email → immediate
Spark run → result filed → processed. The user confirmed: *"it works!"*

## Gotchas learned the hard way

- **MCP tools are for interactive sessions only.** Even the *read* tool
  began prompting after Gemini reset per-app approvals (2026-10-12).
  Scheduled runs must be sheet-only, end to end.
- **Don't deliver a fix for this system through the gated channel itself.**
  A schedule-prompt fix sent *as a bridge request* can't be fetched without
  the very Allow tap that is broken. Edit Gemini Spark's schedules in its
  own UI.
- **Gmail drafts were rejected as a return lane** (they mix with the user's
  real drafts, and send-class actions prompt anyway). Keep/Calendar were
  rejected too (no clean API lane / pollutes real data). Sheets won because
  it is structured, append-only, and has a real read API on both sides.
- **Renames are safe only if everything keys off IDs.** This system keys off
  the spreadsheet **ID** and the **tab names** (`Requests` / `Results` /
  `Notes`). Renaming the spreadsheet *title* (ours was renamed
  `Muse Bridge — Results` → `A2A - Results` on 2026-11-01) breaks nothing
  mechanically — but update every prompt, script string, and doc that
  mentions the old title in the same pass.
- **Debounce matters.** Without it, a multi-row batch insert sends one
  email per change event and Gemini Spark runs repeatedly on an empty queue.
- **Keep request scope read/query-only** on the scheduled lane. Anything
  that books, buys, sends, or deletes belongs in an interactive session
  with a human approving.

## Optional: the interactive MCP layer

The reference setup also runs a small MCP server (a Cloudflare Worker,
OAuth 2.1 + PKCE, dynamic client registration) registered in Gemini as a
custom Connected App, exposing `muse_ping`, `get_pending_requests`,
`submit_request_result`, and `leave_note_for_muse`. It is useful **only**
in live interactive sessions where a human can tap Allow. The scheduled
A2A lane in this guide neither requires it nor uses it — if you are
replicating, build the sheet lane first; add MCP later only if you want
the interactive channel.

## Reference implementation map (ours)

| Piece | Ours |
|---|---|
| Sheet | `A2A - Results` (spreadsheet ID in a local `bridge-sheet.json` config; tabs Results / Requests / Notes) |
| Doorbell | Bound Apps Script `onBridgeChange`, trigger "From spreadsheet — On change" (installed & verified 2026-11-01) |
| Wake signal | Email to the watched Gmail account, subject `A2A-Event` |
| Gemini Spark schedule | `Process Muse bridge requests` — email-triggered, Active; legacy hourly `Check Muse MCP queue` — Paused |
| Muse enqueue | `mcp-queue.py request <kind> '<params-json>' [context]` (mirrors the row into Requests) |
| Muse poller | `sheet-poller.py` + a sheet-poll hook (verify-then-clear; Notes ingestion; Requests pruning) |
| System of record | Muse-side queue store (Cloudflare KV); the sheet is transport only |
